## Three States: Source, Dist, and Installed

skillprism operates on three distinct state layers:

```
Source (Authoring)    ──build──>    Dist (Compilation Output)    ──add / link──>    Installed (Live Agent Paths)
skills/                             dist/                                           .claude/skills/
├── dice-roller/                    ├── claude/skills/dice-roller/                  ~/.claude/skills/
│   ├── skill.yaml                  ├── opencode/skills/dice-roller/                .opencode/skills/
│   └── SKILL.md                    └── codex/skills/dice-roller/                   ~/.config/opencode/skills/
```

### 1. Source (What you author)
Source files live in your skill project repository:
```
skills/dice-roller/
├── skill.yaml       # Metadata: name, description, variables, requirements
├── SKILL.md         # Template: MiniJinja, rendered once per harness
├── references/      # Optional asset directories (copied verbatim)
└── scripts/
```

### 2. Dist (What you compile)
Compiled output is generated by `skillprism build` under `dist/`:
```
dist/
├── claude/skills/dice-roller/SKILL.md
├── opencode/skills/dice-roller/SKILL.md
└── codex/skills/dice-roller/SKILL.md
```
`skillprism build` is compile-only. It renders templates for configured harnesses into `dist/` without polluting your working tree or installed agent directories.

### 3. Installed (What live agents read)
Installed skills are live agent files managed by skillprism's package manager (`add`, `list`, `remove`, `update`, `link`, `unlink`):
- **Project scope (`--target project`)**: Live project paths (e.g. `.claude/skills/`, `.opencode/skills/`)
- **User scope (`--target user`)**: User home paths (e.g. `~/.claude/skills/`, `~/.config/opencode/skills/`)

Skillprism maintains an atomic install manifest (`.skillprism/state.json` or `~/.config/skillprism/state.json`) so installed skills can be tracked, queried (`list`), updated, and cleanly removed.

## Dual Product Framing: Compiler + Package Manager

skillprism acts as both a **compiler** for skill authors and a **package manager** for agent users:

| Role | Commands | Primary Writes | npm Analogy |
|---|---|---|---|
| **Compiler / Author** | `init`, `validate`, `build` | Project source + `dist/` output | `npm init` / `tsc` |
| **Package Manager / Installer** | `add`, `list`, `remove`, `update`, `link`, `unlink` | Live harness directories (`.claude/skills/`, `~/.claude/skills/`) | `npm install` / `npm list` |

## skill.yaml and SKILL.md: two halves of one skill

`skill.yaml` holds **metadata** — name, description, license, variables, and harness-specific config. `SKILL.md` is a **[MiniJinja](https://docs.rs/minijinja) template** that gets rendered with that metadata:

- `skill.yaml` requires `skillprism: '1'`.
- `skill.yaml`'s `name` and `description` become `{{ skill_name }}` and `{{ skill_description }}` in the template.
- `skill.yaml`'s `variables:` entries are available by name in the template.
- Every other `skill.yaml` field (`license`, `when_to_use`, `allowed_tools`, etc.) is available under its own name.

The template can also be named `SKILL.md.j2` if you'd rather the extension say "this is a template" explicitly. Both are accepted, but not both at once in the same skill directory — skillprism errors rather than guessing which one you meant.

## Harnesses

A **harness** is an agent product that reads skills: Claude Code, OpenAI Codex, OpenCode, Factory, Pi. Each has its own:

- **Harness paths** — where it expects to find skill files (e.g. `.claude/skills/` vs `.opencode/skills/`)
- **Capabilities** — what features it supports (subagents, allowed-tools, manifests, frontmatter modes)
- **Length caps** — max name/description lengths (e.g. Claude allows 1536-char descriptions; the spec's portable cap is 1024)
- **Macros** — harness-specific template variables exposed as `{{ harness.<name> }}`

You configure which harnesses your project targets in `skillprism.yaml`. `skillprism build` renders every skill once per configured harness into `dist/`.

## Capability gating

Not every harness supports every feature. A skill can declare `required-capabilities` in `skill.yaml`:

```yaml
required-capabilities:
  - subagent
  - allowed-tools
```

If a harness doesn't support a required capability, that skill-harness pair is **skipped** (not a build failure) — every other pair still builds. You'll see a `[resolve] skipped: ...` warning on stderr.

## Progressive disclosure

The [Agent Skills spec](https://agentskills.io/specification) uses **progressive disclosure** — agents load skill metadata at startup, full instructions only when a task matches, and reference files on demand:

1. **Metadata** (~100 tokens): `name` and `description` are loaded at startup for all skills
2. **Instructions** (<5000 tokens recommended): The full `SKILL.md` body loads when the skill activates
3. **Resources** (as needed): Files in `references/`, `scripts/`, `assets/` load only when required

Keep your main `SKILL.md` under 500 lines. Move detailed reference material to separate files in subdirectories — skillprism copies every subdirectory of a skill verbatim alongside the rendered `SKILL.md`.
